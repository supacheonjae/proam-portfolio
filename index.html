01 / CONTEXT

화면을 바꾸는 일에서,
앱을 다시 설계하는 일로.

기존 WebView 중심 앱을 Flutter 기반 V2로 리뉴얼하며, 주요 기능과 공통 기반을 함께 정비했습니다.

홈, 피드, 클럽, 프로암 이벤트, 보상, 설정으로 이어지는 서비스를 모바일에서 구현했습니다. 기능이 늘어나도 역할을 구분할 수 있는 구조를 만들고, 화면 사이에서 공유되는 데이터와 플랫폼별 동작을 함께 다뤘습니다.

01ARCHITECTURE

기능은 독립적으로,
경계는 일관되게.

화면에서 API와 저장소를 직접 다루지 않도록, 기능별 책임을 네 개의 계층으로 분리했습니다.

해결할 문제

UI, 데이터 접근, 상태 변경이 섞이면 기능 수정이 다른 화면으로 번지기 쉽습니다. 앱 전반에 공통으로 적용할 의존성 방향이 필요했습니다.

선택한 방법

기능 단위로 코드를 묶고 내부를 presentation / application / domain / data로 분리했습니다. Riverpod은 의존성 주입과 상태 연결의 진입점으로 사용했습니다.

구현 결과

화면은 앱 전용 상태와 도메인 데이터를 사용합니다. API 응답 매핑과 플랫폼 연동의 변경 지점을 별도로 두고, 공통 라우팅·딥링크·오류 처리 기반을 함께 구성했습니다.

설계의 경계와 선택 기준 ＋

모든 변환에 별도 UseCase를 만드는 대신, 단순한 화면 전용 매핑은 ViewModel 또는 State에 둡니다. 외부 API·플랫폼 경계는 교체 가능하게 구성하고, 화면을 구성할 때 실제 Repository를 테스트용 구현으로 바꿀 수 있도록 역할을 나눴습니다.

02STATE CONSISTENCY

어느 화면에서 보더라도,
같은 상태를 보여주도록.

빠른 UI 피드백과 서버가 확정한 데이터를 구분하고, 변경 사항을 화면 사이에 전파했습니다.

해결할 문제

목록과 상세의 좋아요 수, 여러 화면의 보유 재화, 로그인 전후의 데이터가 서로 어긋날 수 있습니다. 각각의 화면에서 값을 수정하는 것만으로는 일관성을 유지하기 어렵습니다.

선택한 방법

피드 변경은 공유 Store의 패치로 전달합니다. 보유 재화는 서버를 다시 조회해 확정하고, 로그인 세션 변경 시 revision을 갱신해 관련 상태를 초기화합니다.

구현 결과

재화 값을 화면마다 임의로 증감하지 않고 서버 응답으로 갱신합니다. 피드의 좋아요·댓글 수·본문 변경은 공유 상태를 통해 연결된 화면에 반영합니다.

연속 탭과 실패는 어떻게 처리했나요? ＋

좋아요는 먼저 화면에 반영한 뒤 서버와 동기화합니다. 요청 중 추가 탭이 들어오면 최신 사용자의 의도를 확인해 후속 요청을 이어가고, 서버 응답의 수치와 맞춥니다. 실패 시에는 마지막으로 확정된 상태로 복구합니다. 재화 지급·업로드처럼 중복 부작용이 있는 작업과는 다른 정책입니다.

03MEDIA PIPELINE

원본 그대로 보내기 전에,
표시 목적에 맞게 준비하기.

이미지와 동영상을 앱에서 전처리하고, 업로드 단계에는 준비된 파일을 전달하도록 구성했습니다.

해결할 문제

사용자가 고른 미디어는 크기·비율·회전 정보·형식이 제각각입니다. 작은 목록 이미지부터 상세 보기까지 동일한 원본에 의존하지 않도록 표시 용도를 구분했습니다.

선택한 방법

이미지는 thumbnail·preview·full WebP variant로 준비합니다. 동영상은 메타데이터와 길이를 확인한 후 인코딩하고, 진행 상태를 업로드 흐름에 연결합니다.

구현 결과

미디어 준비와 업로드의 책임을 나눴습니다. GIF는 썸네일에 첫 프레임을 사용하고, preview·full에는 애니메이션을 유지하는 정책으로 처리합니다.

품질과 처리 비용의 균형 ＋

앱 내부 전처리는 단말의 처리 시간과 임시 저장 공간을 사용합니다. 대신 업로드 전에 크기와 형식을 통제할 수 있습니다. 원본의 방향과 비율을 처리하고 동영상 길이를 제한하며, 진행 상태를 전달하는 흐름까지 함께 구현했습니다. 측정하지 않은 용량 절감률이나 속도 개선율은 제시하지 않았습니다.

01 / CONTEXT

화면을 바꾸는 일에서,
앱을 다시 설계하는 일로.

기존 WebView 중심 앱을 Flutter 기반 V2로 리뉴얼하며, 주요 기능과 공통 기반을 함께 정비했습니다.

홈, 피드, 클럽, 프로암 이벤트, 보상, 설정으로 이어지는 서비스를 모바일에서 구현했습니다. 기능이 늘어나도 역할을 구분할 수 있는 구조를 만들고, 화면 사이에서 공유되는 데이터와 플랫폼별 동작을 함께 다뤘습니다.

담당 범위

모바일 아키텍처 · 공통 기반 · 핵심 기능 개발 · Android/iOS 빌드 및 심사 대응 · 출시 후 운영 안정화

기획·디자인·서버와 협업하며 모바일 영역을 담당했습니다. 핵심 리뉴얼은 약 2개월이며, 아래 기술 사례에는 이후 운영 개선도 포함합니다.

03 / ENGINEERING DECISIONS

보이는 화면 뒤의
세 가지 설계.

기능 목록보다, 문제를 나누고 연결한 방법에 집중했습니다.
리뉴얼과 후속 운영 과정에서 구현한 구조를 정리했습니다.

01ARCHITECTURE

기능은 독립적으로,
경계는 일관되게.

화면에서 API와 저장소를 직접 다루지 않도록, 기능별 책임을 네 개의 계층으로 분리했습니다.

해결할 문제

UI, 데이터 접근, 상태 변경이 섞이면 기능 수정이 다른 화면으로 번지기 쉽습니다. 앱 전반에 공통으로 적용할 의존성 방향이 필요했습니다.

선택한 방법

기능 단위로 코드를 묶고 내부를 presentation / application / domain / data로 분리했습니다. Riverpod으로 화면 상태와 공유 상태를 관리했습니다. Repository와 DataSource는 Provider에서 생성·연결해 화면이 구현체를 직접 만들지 않도록 했습니다.

구현 결과

화면은 앱 전용 상태와 도메인 데이터를 사용합니다. API 응답 매핑과 플랫폼 연동의 변경 지점을 별도로 두고, 공통 라우팅·딥링크·오류 처리 기반을 함께 구성했습니다.

설계의 경계와 선택 기준 ＋

모든 변환에 별도 UseCase를 만드는 대신, 단순한 화면 전용 매핑은 ViewModel 또는 State에 둡니다. 의존성 주입은 Provider가 DataSource를 가져와 Repository 생성자에 전달하는 방식으로 구성했습니다. 상태 변화는 ref.watch로 구독하고, 동작 실행에 필요한 객체는 ref.read로 가져옵니다. 개발 시에는 Provider override로 Repository를 테스트용 구현으로 교체할 수 있습니다.

02STATE CONSISTENCY

어느 화면에서 보더라도,
같은 상태를 보여주도록.

빠른 UI 피드백과 서버가 확정한 데이터를 구분하고, 변경 사항을 화면 사이에 전파했습니다.

해결할 문제

목록과 상세의 좋아요 수, 여러 화면의 보유 재화, 로그인 전후의 데이터가 서로 어긋날 수 있습니다. 각각의 화면에서 값을 수정하는 것만으로는 일관성을 유지하기 어렵습니다.

선택한 방법

피드 변경은 공유 Store의 패치로 전달합니다. 보유 재화는 서버를 다시 조회해 확정하고, 로그인·로그아웃 시 세션 변경을 알리는 번호를 갱신해 관련 화면의 상태를 초기화합니다.

구현 결과

재화 값을 화면마다 임의로 증감하지 않고 서버 응답으로 갱신합니다. 피드의 좋아요·댓글 수·본문 변경은 공유 상태를 통해 연결된 화면에 반영합니다.

연속 탭과 실패는 어떻게 처리했나요? ＋

좋아요는 먼저 화면에 반영한 뒤 서버와 동기화합니다. 요청 중 추가 탭이 들어오면 최신 사용자의 의도를 확인해 후속 요청을 이어가고, 서버 응답의 수치와 맞춥니다. 실패 시에는 마지막으로 확정된 상태로 복구합니다. 재화 지급·업로드처럼 중복 부작용이 있는 작업과는 다른 정책입니다.

03MEDIA PIPELINE

원본 그대로 보내기 전에,
표시 목적에 맞게 준비하기.

회사 규모와 서버 운영 부담을 고려해 사진·영상 업로드 구조를 사전에 연구하고, 앱에서 미디어 준비부터 원격 스토리지 업로드까지 수행하도록 구성했습니다.

해결할 문제

사진·영상 업로드 기능에는 파일 전송뿐 아니라 크기별 이미지 생성과 동영상 인코딩이 필요합니다. 이 처리를 서버에 집중시키는 부담을 줄이면서, 목록·상세 화면에 맞는 파일을 제공하고자 했습니다.

선택한 방법

앱에서 용도별 WebP 이미지 3종을 생성하고 동영상을 인코딩합니다. 서버에서 발급받은 서명 기반 업로드 정보로 Blob 스토리지에 직접 전송한 뒤, 업로드 완료와 파일 정보를 서버에 전달합니다.

구현 결과

미디어 준비와 업로드의 책임을 나눴습니다. GIF는 썸네일에 첫 프레임을 사용하고, preview·full에는 애니메이션을 유지하는 정책으로 처리합니다.

품질과 처리 비용의 균형 ＋

서버의 미디어 변환과 파일 중계 부담을 줄이는 대신, 단말의 처리 시간·배터리·임시 저장 공간을 사용합니다. 이를 고려해 이미지 크기와 동영상 길이·해상도를 제한하고 인코딩 진행 상태를 전달했습니다. 단말 성능에 따라 처리 시간이 달라지는 점도 이 선택의 대가입니다.
